## 二、Nitro 部署目标（约 2 分 30 秒）

**【录屏提示】** 屏幕显示 Nitro 的部署目标列表。

Nuxt 的底层是 **Nitro**，它能把项目打包成**多种部署形态**。

**第一，Node 服务。**

```bash
NODE_ENV=production node .output/server/index.mjs
```

**最通用。** 所有渲染模式都支持。**适合自己管理服务器。**

**第二，静态站点。**

```bash
npm run generate
```

**输出纯静态文件。** 只能用于 SSG，**不支持 SSR、ISR、SWR**。

**第三，Serverless。**

部署到 Vercel、Netlify、AWS Lambda。**按需付费，自动扩容。**

**第四，边缘渲染。**

部署到 Cloudflare Workers、Deno Deploy。**全球边缘节点，延迟最低。**

**【录屏提示】** 镜头切回讲师。

**怎么选？**

- **有服务器运维能力** → Node 服务
- **纯静态内容** → 静态托管
- **想省心、流量波动大** → Serverless
- **全球用户、追求极致延迟** → 边缘渲染

**我们课程演示用 Node 服务**，因为它最通用，本地就能跑。

## 三、环境变量（约 2 分 30 秒）

**【录屏提示】** 打开 `.env` 文件。

```bash
# 公开变量（客户端可访问）
NUXT_PUBLIC_SITE_URL=https://example.com
NUXT_PUBLIC_API_BASE=https://api.example.com

# 私有变量（仅服务端可访问）
NUXT_DATABASE_URL=postgres://...
NUXT_SMTP_PASSWORD=xxx
```

**【录屏提示】** 边写边讲。

**安全边界再强调一次：**

**第一，`NUXT_PUBLIC_` 前缀的变量，会被打包进客户端代码，所有人可见。** **绝对不要放密钥。**

**第二，不加前缀的变量，只在服务端可访问。** 通过 `useRuntimeConfig()` 读取。

**第三，`.env` 文件不要提交到 Git。** 加到 `.gitignore`。

**【录屏提示】** 镜头拉近。

**在代码里读取：**

```ts
const config = useRuntimeConfig()

// 客户端可访问
console.log(config.public.siteUrl)

// 仅服务端可访问
console.log(config.databaseUrl)
```

**注意，服务端代码里读 `config.databaseUrl` 没问题，但客户端读会是 `undefined`。** 这是 Nuxt 的保护机制。

## 四、CI/CD 流程（约 2 分 30 秒）

**【录屏提示】** 屏幕显示 CI/CD 流程图。

**CI/CD 的目标是：提交代码后，自动构建、测试、部署。**

我用 **GitHub Actions** 举例。

**【录屏提示】** 新建 `.github/workflows/deploy.yml`。

```yaml
name: Deploy

on:
  push:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm

      - run: npm ci

      - run: npm run lint

      - run: npm run typecheck

      - run: npm run build

      - uses: actions/upload-artifact@v4
        with:
          name: output
          path: .output

  deploy:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - uses: actions/download-artifact@v4
        with:
          name: output

      # 部署到你的服务器
      - name: Deploy
        run: |
          # scp / rsync / docker push ...
```

**【录屏提示】** 边写边讲。

几个关键点。

**第一，`npm ci` 而不是 `npm install`。** `ci` 严格按 `package-lock.json` 安装，更快更可靠。

**第二，`lint` 和 `typecheck` 在 build 之前。** **早失败早发现。**

**第三，构建产物作为 artifact 传给下一个 job。** 避免重复构建。

**第四，部署步骤根据你的目标定制。** 可以是 scp、rsync、Docker、或云平台 CLI。

**【录屏提示】** 镜头拉近。

**别跳过 lint 和 typecheck。** 它们是"自动化的 code review"，能拦截大部分低级错误。

## 五、上线检查清单（约 1 分 30 秒）

**【录屏提示】** 屏幕显示上线清单。

上线前，检查这些：

**第一，环境变量都配好了吗？** 尤其是 API 地址、密钥。

**第二，SEO 元信息都填了吗？** 用 Lighthouse 检查。

**第三，sitemap 和 robots 都生成了吗？** 手动访问确认。

**第四，404 和错误页正常吗？** 手动触发测试。

**第五，性能分数达标吗？** LCP < 2.5s，CLS < 0.1。

**第六，HTTPS 配好了吗？** 现在没有 HTTPS 的站会被浏览器标"不安全"。

**第七，域名和 DNS 解析了吗？** 记得配 `www` 和裸域名的重定向。

**第八，备案信息填了吗？** 国内企业站必须。

## 六、上线后的监控（约 1 分 30 秒）

**【录屏提示】** 镜头切回讲师。

**上线不是终点，是起点。**

**要监控：**

**第一，错误监控。** Sentry、Bugsnag，捕捉运行时错误。

**第二，性能监控。** Web Vitals、Lighthouse CI。

**第三，SEO 监控。** Google Search Console、百度站长平台。

**第四，可用性监控。** UptimeRobot 之类，宕机时告警。

**【录屏提示】** 镜头拉近。

**企业站最常见的"事故"是"上线后没人管"。** 搜索引擎收录掉了、SSL 证书过期了、域名到期了——这些都要监控。
