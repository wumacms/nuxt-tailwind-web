## 二、Nuxt 的约定式目录（约 3 分钟）

先讲清楚 Nuxt 帮我们**约定好了哪些目录**。

**【录屏提示】** 屏幕显示 Nuxt 标准目录结构图。

Nuxt 的核心思想是"**约定优于配置**"。意思是，你把文件放在特定目录，Nuxt 自动帮你处理，不需要写配置。

我们一个个看。

**`pages/`** —— 页面目录。这里每个 `.vue` 文件**自动变成一条路由**。比如 `pages/about.vue` 就对应 `/about`。子目录会自动变成路径层级，`pages/products/index.vue` 对应 `/products`。

**`components/`** —— 组件目录。这里每个组件**自动全局可用**，不需要 `import`。这是 Nuxt 很爽的一点。

**`layouts/`** —— 布局目录。放全站级别的结构，比如默认布局、后台布局。页面通过 `definePageMeta` 指定用哪个。

**`composables/`** —— 组合式函数目录。这里放可复用的逻辑，比如 `useUser`、`useToast`，也是自动导入的。

**`server/`** —— 服务端目录。`server/api/` 下的文件自动变成 API 接口。这是 Nuxt 全栈能力的核心。

**`assets/`** —— 需要构建的资源。比如 CSS、图片、字体。这里的文件会经过 Vite 处理。

**`public/`** —— 静态资源。这里的东西**原样输出**，不经过构建。比如 `favicon.ico`、`robots.txt`。

**【录屏提示】** 镜头切回讲师。

这七个目录，是 Nuxt 项目的基本骨架。**你一定要记住它们的职责，不要乱放。**

## 三、我们项目的目录设计（约 4 分钟）

好，知道了 Nuxt 的约定，我们来看看**这个项目具体怎么组织**。

**【录屏提示】** 在编辑器里逐步创建目录，边建边讲。

我在 Nuxt 默认结构的基础上，做了几层细分。我们一个一个讲。

**第一层，`components/` 下按功能分子目录。**

```text
components/
├── ui/          # 基础 UI 组件：按钮、输入框、卡片
├── layout/      # 布局组件：Header、Footer、Container
├── sections/    # 页面区块：Hero、FeatureGrid、CTA
└── common/      # 通用组件：Icon、Logo、Empty
```

为什么这么分？

`ui/` 是**最基础的零件**，不依赖业务。`layout/` 是**结构骨架**，全站复用。`sections/` 是**页面级区块**，通常只在某些页面用。`common/` 是**杂项**。

这样分的好处是：**找组件的时候，你大概知道去哪找。** 不会出现"这个卡片到底算 ui 还是 section"的纠结——按它被复用的范围判断就行。

**第二层，`composables/` 按领域分。**

```text
composables/
├── useSeo.ts        # SEO 相关
├── useTheme.ts      # 主题切换
├── useToast.ts      # 全局提示
└── useForm.ts       # 表单逻辑
```

每个 composable 对应一个领域。**命名用 `use` 开头**，这是 Vue 生态的约定。

**第三层，`types/` 集中管理类型。**

```text
types/
├── product.ts
├── news.ts
├── common.ts
└── index.ts
```

为什么要有独立的 `types/`？

因为类型是**跨组件共享的契约**。产品类型可能被列表页、详情页、卡片组件同时用到。放一起，改的时候只改一处。

**第四层，`utils/` 放纯函数。**

```text
utils/
├── format.ts     # 日期、数字格式化
├── validate.ts   # 校验函数
└── request.ts    # 请求封装
```

这些是**不依赖 Vue 响应式的纯逻辑**。注意，`utils/` 和 `composables/` 的区别是：`composables` 里可以用 `ref`、`computed`，`utils` 里就是纯函数。

**【录屏提示】** 镜头拉近，语气放慢。

这里我想强调一个**设计思想**：**目录结构不是摆设，它是"职责边界"的物化。**

你把这层想清楚，团队协作时就不会吵架——因为**每个文件该放哪，是有规则的，不是靠感觉的**。

## 四、`assets/` 里的样式组织（约 1 分 30 秒）

好，我们单独讲一下样式目录。

**【录屏提示】** 在 `assets/css/` 下建文件。

```text
assets/css/
├── main.css       # 入口，引入所有
├── theme.css      # 设计令牌 @theme
├── base.css       # 全局基础样式
└── utilities.css  # 自定义工具类 @utility
```

为什么这么分？

`theme.css` 只放**设计令牌**，对应第二章要讲的内容。

`base.css` 放**全局基础样式**，比如 `html`、`body` 的默认设置。

`utilities.css` 放我们**自定义的工具类**。

`main.css` 是入口，把它们按顺序 `@import` 进来。

**【录屏提示】** 打开 `main.css`，写导入。

```css
@import "tailwindcss";
@import "./theme.css";
@import "./base.css";
@import "./utilities.css";
```

**顺序很重要**：Tailwind 先，然后主题，然后基础，最后自定义。

## 五、别过度设计（约 1 分钟）

最后，我要给一个**反向的建议**。

**【录屏提示】** 镜头切回讲师，语气诚恳。

刚才我讲了很多分层，但我要提醒你：**别过度设计。**

如果你做的是一个只有五个页面的小站，搞这么多层反而是负担。你可能直接 `components/` 平铺就够了。

**结构是为项目服务的，不是反过来。** 我的建议是：**先按最简单的来，等痛点出现了，再重构。**

企业项目之所以需要这些分层，是因为它**页面多、迭代久、人多**。你的项目如果不符合这三点，就别硬套。
