# 6.5-数据获取策略

**【录屏提示】** 开场：讲师出镜，背景为 `useFetch` / `useAsyncData` / `$fetch` 三个 API。

---

## 一、开场白（约 30 秒）

好，欢迎回来。

这一节我们讲**数据获取策略**。

Nuxt 提供了三个数据获取 API：`useFetch`、`useAsyncData`、`$fetch`。很多同学第一次看到会懵：**什么时候用哪个？**

这一节，我们把它们讲清楚，并给出**企业项目的数据获取规范**。

---

## 二、三个 API 的区别（约 2 分 30 秒）

**【录屏提示】** 屏幕显示三个 API 的对比表。

**`$fetch`**：底层 API。**最灵活，但不处理 SSR 状态。**

**`useAsyncData`**：包装器。**处理 SSR 状态、避免重复请求，但你要自己写请求逻辑。**

**`useFetch`**：`useAsyncData` + `$fetch` 的组合。**最常用，自动处理请求和状态。**

**【录屏提示】** 镜头切回讲师。

**它们的关系是：`useFetch` = `useAsyncData` + `$fetch`。**

**什么时候用哪个？**

- **`useFetch`**：从 API 取数据。**最常用。**
- **`useAsyncData`**：取数据的逻辑不是简单的 `$fetch`，比如用了 CMS SDK、读了本地文件。**我们 6.4 的 Nuxt Content 就用了这个。**
- **`$fetch`**：**提交动作**（POST、PUT），或者**在事件处理里发请求**。

---

## 三、SSR 状态传递（约 2 分钟）

**【录屏提示】** 屏幕显示 SSR 数据流图。

讲一个**核心机制**：SSR 状态传递。

**企业站用 SSR 时，数据获取发生在服务端。** 服务端取到数据后，渲染成 HTML，同时把数据**序列化到页面里**。

客户端"水合"（hydration）时，**直接读这份数据，不会重新请求。**

**【录屏提示】** 镜头切回讲师。

**这个机制的好处是：不会"闪一下"。** 用户看到的 HTML 和最终状态一致。

**但有个前提：数据要能序列化。** 比如 `Date` 对象、`Map`、函数，都不能直接传。**要用字符串或数字。**

**如果你取的数据里有 `Date` 对象**，SSR 时是 `Date`，客户端水合后变成字符串，会不一致。**这是常见的坑。**

**解决**：在服务端就用 ISO 字符串，客户端需要时再 `new Date()`。

## 四、`useFetch` 的实战用法（约 3 分钟）

**【录屏提示】** 打开一个页面，写 `useFetch`。

```ts
// 基础用法
const { data, pending, error, refresh } = await useFetch('/api/products')

// 带参数
const { data } = await useFetch('/api/products', {
  query: { category: 'software', page: 1 },
})

// 响应式参数
const category = ref('software')
const { data } = await useFetch('/api/products', {
  query: { category },
})

// 转换数据
const { data } = await useFetch('/api/products', {
  transform: (data) => data.map(p => ({
    ...p,
    priceLabel: `¥${p.price}`,
  })),
})

// 懒加载（不阻塞导航）
const { data } = useLazyFetch('/api/products')
```

**【录屏提示】** 边写边讲。

几个关键点。

**第一，`pending` 是加载状态。** 用于显示 skeleton 或 loading。

**第二，`error` 是错误。** 要做错误处理。

**第三，`refresh` 是手动刷新。** 用于"重新加载"按钮。

**第四，响应式参数。** 传 `ref` 或 `computed`，值变化时自动重新请求。**这是筛选功能的关键。**

**第五，`transform` 转换数据。** 在数据到达组件前做处理，避免在模板里写复杂逻辑。

**第六，`useLazyFetch` 不阻塞导航。** 页面先渲染，数据后到。**适合非首屏关键数据。**

**【录屏提示】** 镜头拉近，语气加重。

**`await useFetch` 和 `useLazyFetch` 的区别，是很多人的困惑点。**

- `await useFetch`：**等待数据**，然后渲染页面。SSR 时数据会进 HTML。
- `useLazyFetch`：**不等待**，先渲染，数据后到。SSR 时数据不在 HTML 里。

**首屏关键数据用 `await useFetch`，非关键数据用 `useLazyFetch`。** 这是原则。

## 五、避免重复请求（约 1 分 30 秒）

**【录屏提示】** 镜头切回讲师，语气放慢。

**多个组件请求同一个接口，会重复请求。** 怎么避免？

**给 `useFetch` 一个 key。**

```ts
// 组件 A
const { data } = await useFetch('/api/user', { key: 'user' })

// 组件 B
const { data } = await useFetch('/api/user', { key: 'user' })
```

**【录屏提示】** 镜头拉近。

**相同 key 的请求会被去重。** 组件 B 直接拿组件 A 的结果，不会重复请求。

**默认情况下，Nuxt 会根据 URL 自动生成 key。** 但如果你用了 `transform` 或不同的 options，最好显式指定 key。

## 六、错误处理（约 1 分 30 秒）

**【录屏提示】** 写错误处理。

```ts
const { data, error } = await useFetch('/api/products')

if (error.value) {
  throw createError({
    statusCode: error.value.statusCode || 500,
    statusMessage: '加载失败',
  })
}
```

**【录屏提示】** 镜头切回讲师。

**企业项目必须处理错误。** 不能数据加载失败就白屏。

**两种处理方式：**

**第一，抛错跳到错误页。** 适合"整个页面都加载不出来"的情况。

**第二，局部显示错误提示。** 适合"某个模块加载失败"的情况。

**选择哪种，取决于"这个数据对页面有多重要"。**

## 七、数据获取规范（约 1 分钟）

**【录屏提示】** 屏幕显示规范清单。

我给出企业项目的数据获取规范：

**第一，取数据用 `useFetch`，提交用 `$fetch`。**

**第二，首屏关键数据 `await`，非关键 `useLazyFetch`。**

**第三，统一用 `useAsyncData` 的 key 去重。**

**第四，用 `transform` 做数据转换，不在模板里写逻辑。**

**第五，所有请求都要处理 `error`。**

**第六，敏感数据用 `server/api` 代理，不要直接暴露第三方接口。**
