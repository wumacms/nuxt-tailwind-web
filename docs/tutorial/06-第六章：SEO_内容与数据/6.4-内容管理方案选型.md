# 6.4-内容管理方案选型

**【录屏提示】** 开场：讲师出镜，背景为三种方案的对比图。

## 一、开场白（约 30 秒）

好，欢迎回来。

这一节我们讲**内容管理方案**。

企业站的新闻、案例、产品描述，这些内容**谁来写、怎么改**？如果每次改内容都要开发人员改代码、重新部署，那运营效率太低了。

所以需要一套"内容管理"方案。这一节，我们讲清楚**三种主流方案**，以及怎么选。

---

## 二、三种方案对比（约 3 分钟）

**【录屏提示】** 屏幕显示三种方案的对比表。

**方案一，Markdown + Nuxt Content。**

内容写成 `.md` 文件，放在仓库里。

**优点**：开发友好、版本可控、零外部依赖、免费。

**缺点**：运营人员要会 Git，或者要开发代为提交。

**适合**：内容更新不频繁、团队有技术能力。

**方案二，Headless CMS。**

比如 Strapi、Sanity、Contentful。内容存在 CMS 里，通过 API 提供给前端。

**优点**：有友好的后台界面，运营人员能直接编辑。

**缺点**：要单独部署或付费，有学习成本。

**适合**：内容更新频繁、有专门的运营团队。

**方案三，Git-based CMS。**

比如 TinaCMS、Decap CMS。有后台界面，但内容最终存回 Git。

**优点**：兼顾友好界面和版本控制。

**缺点**：配置略复杂。

**适合**：想要后台界面，又不想引入外部服务。

**【录屏提示】** 镜头切回讲师。

**怎么选？我给出一个判断标准：**

- **内容更新 < 每周一次，团队懂技术** → Markdown + Nuxt Content
- **内容更新频繁，有运营团队** → Headless CMS
- **想要后台界面 + 版本控制** → Git-based CMS

## 三、Nuxt Content 实战（约 3 分钟）

我们课程用的是 **Nuxt Content**，因为它是企业站中小型内容模块的最优解。

**【录屏提示】** 打开 `content/` 目录。

先看目录结构：

```text
content/
├── news/
│   ├── 2025-01-01-award.md
│   └── 2025-02-15-launch.md
├── cases/
│   └── client-a.md
└── products/
    └── software-x.md
```

**【录屏提示】** 打开一个 Markdown 文件。

```markdown
---
title: 公司获得年度创新奖
date: 2025-01-01
category: 公司动态
cover: /images/news/award.jpg
excerpt: 我们很荣幸获得本年度行业创新奖...
author: 市场部
---

## 正文标题

这里是正文内容，支持 **Markdown** 语法。

- 列表项 1
- 列表项 2

> 引用文字

[链接](https://example.com)
```

**【录屏提示】** 镜头切回讲师。

**frontmatter 是 Markdown 顶部的元信息**，用 `---` 包裹。**这些字段可以在页面里通过 `queryContent` 拿到。**

## 四、查询内容（约 2 分钟）

**【录屏提示】** 打开页面，写查询。

```ts
// 查询所有新闻，按日期倒序
const { data: news } = await useAsyncData('news', () =>
  queryContent('/news').sort({ date: -1 }).find()
)

// 查询单篇
const { data: article } = await useAsyncData(`news-${route.path}`, () =>
  queryContent(route.path).findOne()
)

// 只取特定字段
const { data: list } = await useAsyncData('news-list', () =>
  queryContent('/news')
    .only(['title', 'date', 'excerpt', '_path'])
    .sort({ date: -1 })
    .find()
)

// 分页
const { data: page } = await useAsyncData('news-page', () =>
  queryContent('/news')
    .sort({ date: -1 })
    .skip(0)
    .limit(10)
    .find()
)
```

**【录屏提示】** 边写边讲。

几个关键点。

**第一，`.only()` 只取需要的字段。** 减小传输体积。

**第二，`.sort()` 排序。** `-1` 是倒序，`1` 是正序。

**第三，`.skip()` 和 `.limit()` 分页。** `skip` 是跳过多少条，`limit` 是取多少条。

**第四，`.findOne()` 查单篇。** 比 `.find()` 后取第一个更高效。

**【录屏提示】** 镜头拉近。

**`queryContent` 的 API 很像 MongoDB。** 如果你用过 MongoDB，会觉得很熟悉。

## 五、在内容里用 Vue 组件（约 1 分钟）

**【录屏提示】** 屏幕显示 Markdown 里嵌入组件。

Nuxt Content 一个很强大的能力：**Markdown 里可以直接用 Vue 组件。**

```markdown
## 我们的优势

::feature-grid
---
features:
  - icon: zap
    title: 高效
  - icon: shield
    title: 安全
---
::
```

**【录屏提示】** 镜头切回讲师。

**`::component-name` 是 Nuxt Content 的组件语法。** 中间用 frontmatter 形式传 props。

**这样运营人员可以用 Markdown 写内容，同时又能用上你的组件。** 这个能力在做营销落地页时非常好用。

## 六、内容与 SEO 的结合（约 1 分钟）

**【录屏提示】** 镜头切回讲师，语气放慢。

最后提一点：**Nuxt Content 的内容，天然适合 SEO。**

因为它在**构建时或服务端**就能读到，SSR 时直接渲染成 HTML。搜索引擎能抓到完整内容。

**对比一下**：如果是客户端异步取 CMS 数据，首屏是空的，搜索引擎可能抓不到。

**所以，如果你重视 SEO，内容最好在服务端可取。** Nuxt Content 和 SSR 下的 CMS 都满足这个条件。
