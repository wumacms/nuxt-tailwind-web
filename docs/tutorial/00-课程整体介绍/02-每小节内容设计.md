# 每小节内容设计

> 说明：每节按「**本节目标 → 核心知识点 → 实战演示 → 交付产出 →
> 讲解要点/避坑**」统一结构编写，便于直接转化为讲稿与录屏脚本。

---

## 第一章：开篇与项目总览

### 1.1 课程介绍与学习路径

- **本节目标**：让学员明确"学完能得到什么"，建立学习预期与路径感。
- **核心知识点**：课程定位、目标人群、知识地图、最终成品演示。
- **实战演示**：完整企业站成品走查（首页→产品→详情→新闻→联系），逐页展示交互与响应式效果。
- **交付产出**：无（认知建立）。
- **讲解要点/避坑**：强调"这不是 Nuxt 语法课"，避免学员带着"学
  API"的预期进来；明确前置要求（会基础 Vue/TS/CSS）。

### 1.2 技术选型与设计思想

- **本节目标**：讲清楚"为什么是企业站用 Nuxt + Tailwind V4 + TS"。
- **核心知识点**：三者职责边界；Nuxt
  对企业站的价值（SEO、SSR/SSG、约定路由、服务端能力）；Tailwind
  的原子化思想；TS 的工程约束价值。
- **实战演示**：用同一页面在"纯 Vue3 SPA"与"Nuxt SSR"下的 SEO
  表现对比（查看源码、meta 差异）。
- **交付产出**：技术选型决策清单。
- **讲解要点/避坑**：不神化任何技术，讲清"什么场景不该用
  Nuxt"（纯后台系统、强交互 SPA）。

### 1.3 环境搭建与工程初始化

- **本节目标**：从零跑起一个 Nuxt + Tailwind V4 + TS 工程。
- **核心知识点**：`npx nuxi init`、Tailwind V4 的 `@tailwindcss/vite`
  插件方式、`@import "tailwindcss"` 新写法、`nuxt.config.ts` 配置。
- **实战演示**：初始化项目 → 安装 Tailwind → 写第一个带 Tailwind 类的页面 →
  启动验证。
- **交付产出**：可运行的工程骨架 + 初始化脚本。
- **讲解要点/避坑**：V4 不再需要 `tailwind.config.js` 与
  `postcss.config.js`（默认）；讲清 `@tailwindcss/vite` 与 Nuxt 的接入顺序；TS
  严格模式开启。

### 1.4 Nuxt 目录结构与架构设计

- **本节目标**：建立企业级目录规范与分层思想。
- **核心知识点**：`pages/`、`components/`、`layouts/`、`composables/`、`server/`、`assets/`、`types/`、`utils/`
  的职责；约定优于配置。
- **实战演示**：搭建完整目录骨架，用注释标注每层职责；演示自动导入机制。
- **交付产出**：项目目录规范文档 + 空骨架。
- **讲解要点/避坑**：讲清"什么时候该抽 composable、什么时候该建
  component"；避免过度分层。

### 1.5 渲染模式选择

- **本节目标**：理解企业站该如何为不同页面选择渲染策略。
- **核心知识点**：SSR / SSG / SPA / 混合渲染；`routeRules`
  基础；`ssr: true/false` 的取舍。
- **实战演示**：为首页配 SSG、为联系页配 SSR、为后台配 SPA 的 `routeRules`
  示例。
- **交付产出**：渲染策略决策表 + `nuxt.config.ts` 配置。
- **讲解要点/避坑**：讲清"SSG 不是万能"；动态内容页该用
  ISR/SSR；避免学员一股脑全用 SSR。

## 第二章：TailwindCSS V4 在 Nuxt 工程中的落地方式

### 2.1 V4 与 V3 的关键差异

- **本节目标**：让有 V3 经验的学员快速迁移，新学员不被旧资料误导。
- **核心知识点**：CSS-first 配置、`@theme`
  指令、`@utility`、`@variant`、自动内容检测、移除 `tailwind.config.js`。
- **实战演示**：把一段 V3 的 `tailwind.config.js` 改写成 V4 的 `@theme` 写法。
- **交付产出**：V3→V4 迁移对照表。
- **讲解要点/避坑**：重点讲"配置写在哪"的变化；插件生态兼容性；`content`
  自动检测的边界。

### 2.2 `@theme` 定制企业设计令牌

- **本节目标**：把设计稿的 Design Token 映射为 Tailwind 变量。
- **核心知识点**：`@theme`
  语法、`--color-*`、`--font-*`、`--spacing-*`、`--radius-*`、`--shadow-*`
  命名规则。
- **实战演示**：拿一张真实设计稿（Figma），提取品牌色/字体/间距，写入 `main.css`
  的 `@theme`，页面即时生效。
- **交付产出**：企业设计令牌文件 `assets/css/theme.css`。
- **讲解要点/避坑**：命名要与设计稿一致；讲清"哪些该进
  theme、哪些该用任意值"；避免令牌爆炸。

### 2.3 在 Nuxt 组件中组织 Tailwind 类名

- **本节目标**：掌握在 Nuxt SFC 中写 Tailwind 的正确姿势。
- **核心知识点**：静态类 vs 动态类、`:class` 对象/数组语法、`class` 与 `v-bind`
  配合、Nuxt 自动导入组件。
- **实战演示**：写一个带条件样式的按钮，演示静态类保留、动态类拼接的写法。
- **交付产出**：组件类名组织规范。
- **讲解要点/避坑**：**动态拼接类名是 Tailwind 大坑**（如
  `` `text-${color}-500` `` 不会被生成）——重点讲清原理与解法。

### 2.4 抽取可复用样式：`@apply` vs 组件化

- **本节目标**：建立"样式复用"的决策树。
- **核心知识点**：`@apply` 的适用场景、`@utility`
  自定义工具类、组件化的边界、CSS 变量方案。
- **实战演示**：同一段样式分别用
  `@apply`、`@utility`、组件三种方式实现，对比优劣。
- **交付产出**：样式复用决策树图。
- **讲解要点/避坑**：`@apply` 滥用会导致"原子化退化成写
  CSS"；讲清"什么时候不该抽"。

### 2.5 TypeScript 与 Tailwind 的协作

- **本节目标**：用 TS 约束组件样式接口，做到类型安全。
- **核心知识点**：variant 联合类型、props 类型设计、`defineProps`
  泛型、类名映射表类型。
- **实战演示**：用 TS 定义 `ButtonVariant`、`ButtonSize`，并映射到 Tailwind
  类名对象。
- **交付产出**：类型安全的组件样式接口模板。
- **讲解要点/避坑**：讲清"类名映射表"如何避免运行时拼接；TS 类型与 Tailwind
  类名的解耦设计。

### 2.6 响应式与断点策略

- **本节目标**：建立移动优先的响应式开发习惯。
- **核心知识点**：`sm/md/lg/xl/2xl` 默认断点、移动优先、`max-*` 变体、容器查询
  `@container`。
- **实战演示**：把一个桌面版卡片列表改成"移动优先"写法，逐步加断点。
- **交付产出**：响应式断点规范 + 常用布局片段。
- **讲解要点/避坑**：讲清"移动优先"不是口号，是写法顺序；企业站断点要与设计稿栅格对齐。

### 2.7 全局样式与 Nuxt 配置整合

- **本节目标**：把 Tailwind 与 Nuxt 的全局配置打通。
- **核心知识点**：`nuxt.config.ts` 的 `css` 字段、`app.config.ts`
  运行时配置、全局样式分层。
- **实战演示**：注入 `theme.css`、`main.css`，用 `app.config.ts`
  控制品牌名/主题色。
- **交付产出**：Nuxt + Tailwind 全局配置模板。
- **讲解要点/避坑**：讲清"构建时配置（`nuxt.config`）"与"运行时配置（`app.config`）"的区别与选择。

## 第三章：企业网站通用布局系统

### 3.1 布局设计思想

- **本节目标**：建立"布局系统"而非"逐页写布局"的思维。
- **核心知识点**：栅格系统、容器、间距节奏、视觉层次。
- **实战演示**：用一张企业站设计稿，拆解出"容器 + 栅格 + 间距"三要素。
- **交付产出**：布局设计原则文档。
- **讲解要点/避坑**：讲清"统一布局系统"对企业站可维护性的价值。

### 3.2 Nuxt Layouts 实战

- **本节目标**：用 Nuxt 布局机制承载企业站结构。
- **核心知识点**：`layouts/default.vue`、具名布局、`definePageMeta({ layout })`、布局与页面解耦。
- **实战演示**：建 `default`（前台）与 `admin`（后台）两套布局并切换。
- **交付产出**：多套布局模板。
- **讲解要点/避坑**：讲清"布局放结构、页面放内容"的边界；避免把业务逻辑塞进
  layout。

### 3.3 页面容器与最大宽度策略

- **本节目标**：封装统一容器组件，解决全站宽度一致性问题。
- **核心知识点**：`container`、`max-w-*`、`mx-auto`、自定义容器组件。
- **实战演示**：封装 `<AppContainer>`，支持 `size`
  变体（narrow/default/wide/full）。
- **交付产出**：`AppContainer` 组件。
- **讲解要点/避坑**：讲清"为什么不用 Tailwind 内置
  container"；容器与内边距的配合。

### 3.4 顶部导航栏（Header）

- **本节目标**：实现一个企业站级别的高可用 Header。
- **核心知识点**：`fixed/sticky`
  定位、滚动监听变色、移动端抽屉菜单、下拉菜单、过渡动画。
- **实战演示**：从静态 Header → 滚动变色 → 移动端汉堡菜单 →
  下拉二级菜单，逐步增强。
- **交付产出**：`AppHeader` 组件（含移动端）。
- **讲解要点/避坑**：滚动监听性能（`passive`、节流）；移动端菜单的焦点管理与滚动锁定。

### 3.5 页脚（Footer）

- **本节目标**：实现信息架构清晰的 Footer。
- **核心知识点**：多列栅格、响应式折叠、社交图标、版权栏、备案信息。
- **实战演示**：桌面四列 → 平板两列 → 移动单列的响应式 Footer。
- **交付产出**：`AppFooter` 组件。
- **讲解要点/避坑**：讲清"Footer 是企业站信息架构的收口"；列数变化用断点而非
  JS。

### 3.6 侧边栏与面包屑

- **本节目标**：实现内容型页面的侧边导航与路径提示。
- **核心知识点**：侧边栏布局、`sticky`、面包屑生成、响应式收起。
- **实战演示**：为"新闻详情页"加侧边栏（相关文章）+ 面包屑。
- **交付产出**：`AppSidebar` + `AppBreadcrumb` 组件。
- **讲解要点/避坑**：面包屑的数据来源设计（路由 meta vs 数据驱动）。

### 3.7 布局组件化与插槽设计

- **本节目标**：把布局抽象为可复用组件，讲清组件 API 设计思想。
- **核心知识点**：默认插槽、具名插槽、作用域插槽、props 设计、组合优于继承。
- **实战演示**：封装 `<PageSection>`（标题+副标题+内容插槽），全站复用。
- **交付产出**：一组布局级组件。
- **讲解要点/避坑**：讲清"插槽是布局组件的灵魂"；避免 props 过多导致 API 臃肿。

## 第四章：核心 UI 组件实战

### 4.1 按钮系统

- **本节目标**：打造类型安全、可扩展的按钮系统。
- **核心知识点**：variant/size 设计、TS 联合类型、类名映射表、loading/disabled
  状态、图标位。
- **实战演示**：用 TS 定义 variant 类型 → 映射 Tailwind 类 → 渲染所有组合。
- **交付产出**：`AppButton` 组件 + 类型定义。
- **讲解要点/避坑**：类名映射表 vs 动态拼接；`as`
  属性支持（button/a/router-link）。

### 4.2 表单组件

- **本节目标**：实现一套风格统一、状态完整的表单控件。
- **核心知识点**：Input/Textarea/Select、`focus/error/disabled`
  状态类、`peer`/`has` 变体、label 关联、错误提示。
- **实战演示**：实现带校验状态的输入框，演示 `has-[:invalid]` 等新变体。
- **交付产出**：表单控件组件集 + 校验状态样式。
- **讲解要点/避坑**：V4 的 `has-*`、`group-*`、`peer-*` 变体用法；a11y 的
  `aria-invalid` 配合。

### 4.3 卡片组件

- **本节目标**：实现企业站高频的多种卡片。
- **核心知识点**：产品卡、新闻卡、团队卡、hover 效果、图片比例、内容截断。
- **实战演示**：同一卡片组件通过插槽/配置支持三种形态。
- **交付产出**：`AppCard` 系列组件。
- **讲解要点/避坑**：图片比例用 `aspect-*`；文本截断用 `line-clamp-*`；hover
  动效克制。

### 4.4 导航与标签

- **本节目标**：实现 Tabs、面包屑、分页等导航类组件。
- **核心知识点**：状态驱动样式、`aria-selected`、键盘导航、分页逻辑。
- **实战演示**：实现一个可键盘操作的 Tabs 组件。
- **交付产出**：`AppTabs`、`AppPagination` 组件。
- **讲解要点/避坑**：讲清"样式随状态变"的统一模式（用 data 属性 + Tailwind
  变体）。

### 4.5 反馈组件

- **本节目标**：实现 Toast、Modal、Drawer、Tooltip。
- **核心知识点**：`<Teleport>`、过渡动画、`transition`
  体系、焦点陷阱、滚动锁定。
- **实战演示**：实现 Modal 与 Drawer，演示进出场动画。
- **交付产出**：反馈组件集 + composable（`useToast`）。
- **讲解要点/避坑**：SSR 下 `<Teleport>` 的水合问题；焦点管理与 Esc
  关闭；`prefers-reduced-motion`。

### 4.6 数据展示

- **本节目标**：实现表格、列表、统计卡片。
- **核心知识点**：响应式表格（移动端卡片化）、斑马纹、排序指示、统计卡数字动效。
- **实战演示**：桌面表格 → 移动端转卡片列表的响应式实现。
- **交付产出**：`AppTable`、`StatCard` 组件。
- **讲解要点/避坑**：讲清"响应式表格不是缩小，是换形态"；避免横向滚动条。

### 4.7 组件库组织与导出

- **本节目标**：把散落组件组织成企业级组件库。
- **核心知识点**：Nuxt 自动导入、目录约定、命名规范、`components/`
  分层、组件文档。
- **实战演示**：整理组件目录，配置自动导入前缀，生成组件清单。
- **交付产出**：组件库目录规范 + 索引文档。
- **讲解要点/避坑**：讲清"什么时候该加前缀"；避免组件命名冲突；自动导入的边界。

## 第五章：企业官网核心页面实战

### 5.1 首页（Home）

- **本节目标**：完成企业站门面，讲清"首屏视觉 + 转化路径"设计。
- **核心知识点**：Hero 区、价值主张、产品/优势、案例、CTA、合作伙伴、滚动动效。
- **实战演示**：从设计稿逐区块实现首页，边写边讲转化路径设计。
- **交付产出**：完整首页 `pages/index.vue`。
- **讲解要点/避坑**：首屏 LCP 优化；Hero 图用 `NuxtImg`；动效不要拖慢首屏。

### 5.2 关于我们（About）

- **本节目标**：实现信息密集型页面。
- **核心知识点**：公司介绍、发展历程时间轴、团队、企业文化、图文混排。
- **实战演示**：用 Tailwind 实现一条响应式时间轴。
- **交付产出**：`pages/about.vue` + 时间轴组件。
- **讲解要点/避坑**：时间轴的连接线实现（伪元素 vs 边框）；图文混排的栅格。

### 5.3 产品/服务页（Products）

- **本节目标**：实现列表 + 动态详情页。
- **核心知识点**：文件路由、`[slug].vue`、动态路由参数、分类筛选、`useFetch`
  取数。
- **实战演示**：列表页 → 点击进详情 → 详情页 SEO 动态 meta。
- **交付产出**：`pages/products/index.vue` + `[slug].vue`。
- **讲解要点/避坑**：筛选状态同步到 URL query；详情页的 `useSeoMeta` 动态化；404
  处理。

### 5.4 新闻/博客页（News）

- **本节目标**：实现内容型页面与富文本排版。
- **核心知识点**：列表、分类、详情、富文本渲染、Tailwind Typography 插件。
- **实战演示**：用 `prose` 类渲染富文本，定制企业风格排版。
- **交付产出**：`pages/news/*` + 富文本样式。
- **讲解要点/避坑**：`prose` 的自定义（`prose-headings:` 等）；富文本的 XSS
  防护。

### 5.5 案例展示页（Cases）

- **本节目标**：实现复杂布局与交互的展示页。
- **核心知识点**：瀑布流（`columns`）、画廊、灯箱、筛选、懒加载。
- **实战演示**：用 CSS `columns` 实现响应式瀑布流 + 灯箱预览。
- **交付产出**：`pages/cases.vue` + 灯箱组件。
- **讲解要点/避坑**：瀑布流用 CSS 还是 JS；灯箱的键盘导航与焦点管理。

### 5.6 联系我们（Contact）

- **本节目标**：打通"表单 → 服务端 → 反馈"完整链路。
- **核心知识点**：表单设计、`server/api` 接口、服务端校验、提交状态、地图嵌入。
- **实战演示**：前端表单 → `server/api/contact.post.ts` → 校验 → 返回 → Toast
  反馈。
- **交付产出**：`pages/contact.vue` + 服务端接口。
- **讲解要点/避坑**：前后端双重校验；防重复提交；地图的懒加载与隐私合规。

### 5.7 404 与通用错误页

- **本节目标**：实现品牌化的错误页。
- **核心知识点**：`error.vue`、错误状态处理、品牌一致性、引导回首页。

# 2.2 `@theme` 定制企业设计令牌

**【录屏提示】** 开场镜头：讲师出镜，背景为设计稿（Figma）与代码编辑器双屏。

## 一、开场白（约 30 秒）

好，欢迎回到课程。上一节我们讲了 Tailwind V4 和 V3
的关键差异，其中最重要的一个变化，就是配置方式从 `tailwind.config.js` 搬到了 CSS
里，用的是 `@theme` 这个指令。

那这一节，我们就正式来用它。我们要做的事情很具体：**把一张真实的企业站设计稿，变成代码里的设计令牌。**

这是整个项目的地基。地基打得好，后面所有页面、所有组件，风格才能统一，改起来才不痛苦。

**【录屏提示】** 切到 Figma 设计稿全貌，鼠标圈出颜色、字体、间距等标注。

---

## 二、先讲清楚：什么是设计令牌（约 1 分 30 秒）

在动手之前，我们先统一一个概念——**设计令牌**，英文叫 Design Token。

你可以把它理解成：**设计稿里那些会被反复使用的"最小设计决策"**。

比如说，品牌主色是
`#2563EB`，这个颜色在按钮上、在链接上、在图标上都会用到。那它就不应该是一个"随手写的色值"，而应该是一个**有名字的令牌**，比如
`brand-primary`。

再比如，全站正文行高是 1.7，圆角统一是
8px，卡片阴影是某一套固定的值——这些都是令牌。

那为什么企业项目一定要有令牌？

我讲三个理由：

**第一，一致性。**
没有令牌，十个页面可能出现五种不同的蓝色，因为每个人凭感觉取色。

**第二，可维护性。** 品牌色要改，有令牌的话，改一个地方，全站生效。

**第三，协作效率。** 设计师和开发说的是一套语言。设计师说"用主色"，开发知道就是
`brand-primary`，不用来回对色值。

所以在 Tailwind V4 里，`@theme` 就是**承载这套令牌的地方**。

**【录屏提示】** 切到编辑器，新建 `assets/css/theme.css`。

---

## 三、`@theme` 的基本语法（约 2 分钟）

好，我们打开代码。我新建一个文件，叫 `assets/css/theme.css`。

`@theme` 的写法非常直观，它本质上就是**定义 CSS 变量**，只不过用了 Tailwind
规定的命名前缀。

我写一个最简单的例子：

```css
@import "tailwindcss";

@theme {
  --color-brand-500: #2563eb;
}
```

**【录屏提示】** 边写边讲解，写完后停顿。

这里有几个点要讲清楚。

**第一，`@theme` 必须配合 `@import "tailwindcss"` 使用。**
你可以写在同一个文件里，也可以分开。我个人的习惯是——把 `@import` 放在入口文件
`main.css`，把 `@theme` 单独放一个 `theme.css`，然后在 `main.css` 里 `@import`
进来。这样结构更清晰。

**第二，命名是有规则的。** 你看 `--color-brand-500`，这个 `--color-` 前缀是
Tailwind 规定的，意思是"我定义的是一个颜色令牌"。后面的 `brand-500`
就是它的名字。

一旦你这样定义了，Tailwind
就会**自动生成对应的工具类**。也就是说，我现在可以直接在模板里写
`bg-brand-500`、`text-brand-500`、`border-brand-500`——不需要任何额外配置。

**第三，这一点很关键。** 你定义的令牌，**会覆盖 Tailwind
的默认值，或者作为新值加入**。比如你定义了 `--color-brand-500`，那
`bg-brand-500` 就能用了，同时 Tailwind 原本的 `bg-blue-500` 依然存在。

**【录屏提示】** 在页面里写一个 `bg-brand-500` 的 div，保存，浏览器实时生效。

好，你看，页面已经变蓝了。这就是 `@theme` 的威力——**定义一次，全站可用**。

## 四、完整定义一套企业令牌（约 4 分钟）

好，基础知识讲完，我们来干正事。现在看设计稿。

**【录屏提示】** 切到 Figma，逐项圈出标注。

设计稿里，我们的企业站有这些设计决策：

- **品牌色**：主色是一套蓝色，从浅到深有 9 个梯度；还有一个强调色，是橙色。
- **中性色**：灰阶，用于文字、边框、背景。
- **字体**：中文用系统字体栈，英文用 Inter。
- **圆角**：小元素 6px，卡片 12px，大容器 20px。
- **阴影**：卡片有一层柔和的阴影。
- **间距**：基于 4px 的倍数。

好，我们一项一项来写。

**【录屏提示】** 在 `theme.css` 中逐段书写，每写一段切浏览器验证。

**颜色部分：**

```css
@theme {
  /* 品牌色 */
  --color-brand-50: #eff6ff;
  --color-brand-100: #dbeafe;
  --color-brand-200: #bfdbfe;
  --color-brand-300: #93c5fd;
  --color-brand-400: #60a5fa;
  --color-brand-500: #2563eb;
  --color-brand-600: #1d4ed8;
  --color-brand-700: #1e40af;
  --color-brand-800: #1e3a8a;
  --color-brand-900: #1e3a8a;

  /* 强调色 */
  --color-accent-500: #f97316;
  --color-accent-600: #ea580c;
}
```

这里我讲一个**设计思想**。为什么品牌色要定义 9 个梯度，而不是一个颜色？

因为在真实界面里，同一个品牌色会出现在不同场景：hover
时要深一点，禁用时要浅一点，浅色背景要淡一点。**如果你只有一个色值，就会到处硬编码，最后失控。**

梯度化，是专业设计系统的基本功。

**字体部分：**

```css
--font-sans: "Inter", "PingFang SC", "Microsoft YaHei", system-ui, sans-serif;
--font-display: "Inter", "PingFang SC", system-ui, sans-serif;
```

`--font-*` 定义后，就能用 `font-sans`、`font-display` 这些类。

这里讲一下**字体栈的顺序思想**：英文在前，中文在后，系统字体兜底。这样英文用
Inter 渲染，中文自动回退到苹方或微软雅黑，跨平台观感统一。

**圆角部分：**

```css
--radius-sm: 6px;
--radius-md: 12px;
--radius-lg: 20px;
```

对应 `rounded-sm`、`rounded-md`、`rounded-lg`。

**阴影部分：**

```css
--shadow-card: 0 2px 8px rgb(0 0 0 / 0.06), 0 8px 24px rgb(0 0 0 / 0.04);
```

对应 `shadow-card`。

这里顺带说一句，Tailwind 默认的 `shadow-sm`、`shadow-md`
在企业站里往往偏重，所以我通常会**自定义一套更柔和的阴影**，让卡片看起来更精致。

**间距部分：**

```css
--spacing: 0.25rem;
```

`--spacing` 是 V4 里比较特殊的一个令牌——它是**间距的基准单位**。你设成
`0.25rem`，那 `p-4` 就等于 `1rem`。这个一般不用改，知道它存在就行。

好，写到这里，我们的令牌体系就成型了。

**【录屏提示】** 切浏览器，打开 DevTools，指着 CSS 变量面板。

你看，所有令牌都以 CSS 变量的形式存在，可以在运行时被读取、被覆盖。这就是为什么
V4 的主题能力比 V3 更强——**它不只是构建时的配置，还是运行时的变量。**

## 五、在 Nuxt 里接入（约 1 分钟）

令牌写好了，怎么让 Nuxt 用上？

**【录屏提示】** 打开 `nuxt.config.ts`。

在 `nuxt.config.ts` 里，把入口 CSS 注入进去：

```ts
export default defineNuxtConfig({
  css: ["~/assets/css/main.css"],
});
```

然后在 `main.css` 里：

```css
@import "tailwindcss";
@import "./theme.css";
```

这样，`@theme` 就生效了。

**注意顺序**：`@import "tailwindcss"` 要在前面，`theme.css`
在后面。因为主题是**基于 Tailwind 的命名规则去扩展**的。
