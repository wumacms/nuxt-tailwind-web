**【录屏提示】** 开场：讲师出镜，背景为代码审查画面。

## 一、开场白（约 30 秒）

好，欢迎回来。

这一节我们讲**代码规范与团队协作**。

前面我们做了很多技术工作。但**企业项目的成功，不只靠技术，更靠"协作"**。代码规范、目录约定、提交规范、Code Review——这些决定了项目能否**长期维护**。

---

## 二、为什么需要规范（约 1 分 30 秒）

**【录屏提示】** 屏幕显示"规范"和"混乱"的对比。

**规范不是为了"限制自由"，是为了"降低沟通成本"。**

举个例子：如果每个人命名风格不同，A 写 `getUserInfo`，B 写 `fetch_user_data`，C 写 `GetUserInfo`——**读代码时你要不断切换思维。**

**规范统一后，你读任何人的代码都"顺"。**

**【录屏提示】** 镜头切回讲师。

**企业项目生命周期长，人员会流动。** 规范是"让新人快速上手"的关键。

---

## 三、命名规范（约 2 分 30 秒）

**【录屏提示】** 屏幕显示命名规范清单。

我给出企业项目的命名规范。

**第一，组件名用大驼峰。**

`AppButton.vue`、`PageSection.vue`。

**第二，通用组件加 `App` 前缀。**

`AppButton`、`AppCard`。**避免和第三方组件混淆。**

**第三，composable 用 `use` 开头，小驼峰。**

`useTheme.ts`、`useToast.ts`。

**第四，工具函数用动词开头，小驼峰。**

`formatDate.ts`、`validateEmail.ts`。

**第五，类型用大驼峰，不加 `I` 前缀。**

```ts
interface Product { ... }  // 好
interface IProduct { ... } // 不好
```

**第六，常量用大写下划线。**

```ts
const API_BASE_URL = '...'
```

**第七，CSS 变量用小写连字符。**

```css
--color-primary: ...
```

**【录屏提示】** 镜头拉近。

**核心原则是：让"名字"表达"意图"。** `getUserById` 比 `getUser` 更清楚。

---

## 四、目录约定（约 1 分 30 秒）

**【录屏提示】** 镜头切回讲师。

目录约定我们 1.4 讲过，这里再强调几点。

**第一，`components/` 按功能分层。** `ui/`、`layout/`、`sections/`、`common/`。

**第二，`composables/` 按领域命名。** `useTheme`、`useToast`。

**第三，`types/` 集中管理。** 跨组件共享的类型放这里。

**第四，`server/api/` 按资源命名。** `products.get.ts`、`contact.post.ts`。

**第五，`content/` 按内容类型分目录。** `news/`、`cases/`。

**【录屏提示】** 镜头切回讲师。

**约定要写进文档。** 新人入职，第一件事是读目录规范。

---

## 五、Git 提交规范（约 2 分钟）

**【录屏提示】** 屏幕显示提交规范。

**提交信息要能"读懂"。**

我推荐 **Conventional Commits** 规范：

```text
feat: 新增产品详情页
fix: 修复导航栏滚动变色失效
docs: 更新组件清单文档
style: 格式化代码
refactor: 重构按钮组件
perf: 优化首页图片加载
test: 添加表单校验测试
chore: 升级依赖
```

**【录屏提示】** 边写边讲。

**格式是 `类型: 描述`。**

**好处是：**

**第一，一眼看懂这次提交"做了什么"。**

**第二，可以自动生成 CHANGELOG。**

**第三，可以按类型过滤（比如只看 `fix`）。**

**【录屏提示】** 镜头切回讲师。

**可以用 `commitlint` + `husky` 自动校验。**

```bash
npm install -D @commitlint/cli @commitlint/config-conventional husky
```

**配置后，不符合规范的提交会被拒绝。** 这样团队提交质量有保证。

## 六、Code Review 要点（约 2 分钟）

**【录屏提示】** 屏幕显示 Review 清单。

**Code Review 不是"挑刺"，是"共同把关"。**

我给出企业项目的 Review 要点：

**第一，逻辑正确吗？** 有没有边界情况没处理？

**第二，命名清楚吗？** 别人能看懂吗？

**第三，有重复代码吗？** 能不能抽出来？

**第四，有性能问题吗？** 有没有不必要的重渲染、重复请求？

**第五，有安全问题吗？** 有没有 XSS、密钥泄漏？

**第六，有测试吗？** 关键逻辑有没有覆盖？

**第七，符合项目规范吗？** 命名、目录、提交信息。

**【录屏提示】** 镜头拉近，语气放慢。

**Review 的原则是"对事不对人"。**

**评论要具体、可操作。** 不要写"这里不好"，要写"这里可以抽成组件，因为 X 页面也用了同样的结构"。

**也不要"吹毛求疵"。** 小的风格问题交给工具（Prettier、ESLint）自动处理，Review 聚焦在"设计"和"逻辑"上。

---

## 七、文档（约 1 分钟）

**【录屏提示】** 镜头切回讲师。

**文档是团队协作的"基础设施"。**

我推荐几份必备文档：

**第一，`README.md`。** 项目简介、启动方式、目录结构。

**第二，`components/README.md`。** 组件清单，每个组件的用途和 props。

**第三，`CONTRIBUTING.md`。** 贡献指南，命名规范、提交规范。

**第四，`CHANGELOG.md`。** 版本变更记录。

**【录屏提示】** 镜头拉近。

**文档不用写得"很美"，但要"有用"。** 新人能靠它上手，就是好文档。
